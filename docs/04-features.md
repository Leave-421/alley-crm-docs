# 기능 명세 · 인수 조건

> 상태: 초안 (2026-11-23). 요구사항마다 '이렇게 확인하면 통과'인 조건을 적는다.
> 기준: [`03-requirements.md`](03-requirements.md)(무엇을), [`05-policy.md`](05-policy.md)(규칙과 숫자), [`06-data.md`](06-data.md)(기록). 서로 다르면 요구사항 → 정책 순으로 따르고, 어긋난 곳은 고친다.
> 처음에는 **화면 구성과 묶이지 않은 규칙 · 서버 동작**만 담았고, 화면이 정해진 뒤(확정 목업, [11-24 (4)](reviews/decision-meeting-2026-11-24-4.md)) 화면에 묶인 요구사항(MAP · NTF · FR-CRS-02 · FR-CPN-09 · FR-ANL-03 · 04 · 08 · 비기능 일부)도 [`07-screens.md`](07-screens.md)와 [`ARCHITECTURE.md`](ARCHITECTURE.md)를 기준으로 채웠다.

## 읽는 법

- 한 줄이 조건 하나다. **상황**에서 **행동**을 하면 **기대 결과**가 나와야 통과다.
- 기대 결과는 화면 모양이 아니라 서버가 지키는 결과(상태 · 기록 · 금액 · 거절)로 쓴다. '거절'은 요청이 처리되지 않고 상태가 바뀌지 않는다는 뜻이다. 에러 코드는 개발 저장소 계약 문서에서 정한다. 화면에 묶인 요구사항 행은 화면에 보여야 하는 것(07-screens의 '꼭 있어야 할 것')을 기대 결과로 쓴다.
- 숫자는 설정값의 기본값을 쓴다(수수료 4%, 소개 예약 신청 마감 = 기준 가게 예약일 당일 종료, 재방문 60일, 쿠폰 30일 · 7×24시간, 일부 환불 50% 예시, k = 10, 최소 5명).
